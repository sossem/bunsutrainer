bunsutrainer GitHub 작업 운영 매뉴얼
====================================

목적
----
이 매뉴얼은 집 PC와 사무실 PC에서 같은 GitHub 저장소를 이어서 작업하면서,
현재 배포 중인 main 브랜치와 대대적인 개선 작업용 redesign 브랜치를 안전하게 관리하기 위한 절차입니다.

프로젝트 기본 구조
------------------
bunsutrainer
├─ index.html
├─ elementaryschooldata.json
├─ 기타 프로젝트 파일
└─ 작업툴(bat)
   ├─ 작업시작.bat
   └─ 작업종료.bat

브랜치 역할
-----------
main
- 현재 실제 배포 중인 안정 버전
- GitHub Pages가 이 브랜치를 기준으로 배포되는 경우가 많음
- 큰 수정은 가급적 직접 하지 않음

redesign
- 대대적인 개선 작업용 브랜치
- UI 변경, 구조 개선, 기능 추가 등을 여기서 진행
- 충분히 테스트한 뒤 main에 병합

핵심 원칙
---------
1. 작업 시작은 항상 작업시작.bat으로 한다.
2. 작업 시작 시 현재 브랜치를 반드시 확인한다.
3. 대대적인 개선 작업은 redesign 브랜치에서 한다.
4. 작업 종료 전 변경사항을 확인한다.
5. 작업 종료는 작업종료.bat으로 한다.
6. 브랜치를 바꾸기 전에는 git status를 확인한다.
7. 변경사항이 남아 있으면 먼저 commit/push 한 뒤 브랜치를 바꾼다.
8. main에 push하면 실제 배포 버전에 영향을 줄 수 있으므로 특히 주의한다.

==================================================
1. 작업 시작
==================================================

1) 작업툴(bat) 폴더의 작업시작.bat 실행

작업시작.bat은 자동으로 다음 작업을 수행합니다.

- 프로젝트 루트 폴더로 이동
- 현재 Git 브랜치 확인
- main 브랜치라면 경고 표시
- GitHub 최신 파일 가져오기(git pull)
- VS Code 실행
- index.html 자동 열기

정상 예시

현재 브랜치: redesign

GitHub 최신 파일 가져오는 중...
Already up to date.

작업 준비 완료
현재 브랜치: redesign

주의
----
현재 브랜치가 main으로 표시되는데 대대적인 개선 작업을 하려는 경우,
바로 수정하지 말고 redesign으로 이동합니다.

VS Code 터미널에서:

git switch redesign

확인:

git branch

예시:

  main
* redesign

* 표시가 현재 작업 중인 브랜치입니다.

==================================================
2. 작업 중
==================================================

redesign 브랜치에서 평소처럼 작업합니다.

예:
- index.html 수정
- Codex를 이용한 기능 개선
- UI 개선
- 코드 구조 변경
- 버그 수정

로컬 테스트가 필요하면 VS Code 터미널에서:

python -m http.server 8000 --bind 127.0.0.1

브라우저 주소:

http://localhost:8000

서버 종료:

Ctrl + C

서버를 실행한 터미널은 서버 전용으로 두고,
Git 명령은 새 터미널을 하나 더 열어서 사용하는 것이 편합니다.

==================================================
3. 현재 상태 확인
==================================================

작업 중 언제든 현재 상태가 궁금하면:

git status

현재 브랜치 확인:

git branch

또는:

git branch --show-current

GitHub와 동기화 상태까지 확인할 때는 git status가 가장 유용합니다.

예:

On branch redesign
Your branch is up to date with 'origin/redesign'.

nothing to commit, working tree clean

뜻:
- redesign 브랜치에 있음
- GitHub와 동일함
- 저장되지 않은 변경사항 없음

==================================================
4. 작업 종료
==================================================

작업이 끝나면 작업툴(bat) 폴더의 작업종료.bat을 실행합니다.

작업종료.bat은 자동으로 다음을 수행합니다.

1. 현재 브랜치 확인
2. main이면 경고 및 계속 여부 질문
3. 변경사항 확인
4. git status 표시
5. 커밋 메시지 입력 요청
6. git add .
7. git commit
8. git pull --rebase
9. git push
10. 완료 메시지 표시

커밋 메시지는 짧고 구체적으로 작성합니다.

좋은 예:
- 메인 화면 UI 개선
- 문제 출제 로직 수정
- 타이머 입력 오류 수정
- 모바일 화면 배치 개선

피하면 좋은 예:
- 수정
- 업데이트
- 작업함

==================================================
5. main 브랜치 경고가 뜰 때
==================================================

작업종료.bat 실행 중 다음과 같은 경고가 나오면:

[주의] 현재 main 브랜치입니다.
이 브랜치의 Push는 실제 배포 버전에 영향을 줄 수 있습니다.

대대적인 개선 작업 중이라면 N을 눌러 종료를 취소합니다.

그 후 VS Code 터미널에서:

git switch redesign

다시 작업 내용을 확인한 뒤 작업을 이어갑니다.

단, 브랜치를 바꾸기 전에 반드시:

git status

를 확인합니다.

변경사항이 남아 있으면 먼저 저장(commit)해야 안전합니다.

==================================================
6. main ↔ redesign 브랜치 전환
==================================================

개선판으로 이동:

git switch redesign

기존 배포판으로 이동:

git switch main

전환 전 권장 절차:

git status

변경사항이 있으면:

git add .
git commit -m "현재 작업 저장"
git push

그 다음:

git switch main

또는:

git switch redesign

==================================================
7. 집 PC와 사무실 PC를 번갈아 사용할 때
==================================================

권장 흐름:

[집 PC 작업 종료]
작업종료.bat
→ commit
→ pull --rebase
→ push

[사무실 PC 작업 시작]
작업시작.bat
→ 현재 브랜치 확인
→ git pull
→ VS Code 실행

[사무실 PC 작업 종료]
작업종료.bat
→ commit
→ pull --rebase
→ push

[집 PC 작업 시작]
작업시작.bat
→ git pull
→ 최신 상태에서 이어서 작업

중요:
한 PC에서 작업을 끝낸 뒤 push하지 않고 다른 PC에서 작업을 시작하면
서로 다른 버전이 생길 수 있으므로 가능하면 항상 작업종료.bat까지 실행합니다.

==================================================
8. redesign 작업이 완성되었을 때
==================================================

redesign에서 충분히 테스트합니다.

1) 현재 상태 확인

git status

2) 변경사항이 남아 있으면 저장

git add .
git commit -m "redesign 최종 작업"
git push

3) main으로 이동

git switch main

4) main 최신 상태 가져오기

git pull

5) redesign을 main에 병합

git merge redesign

6) 문제 없으면 GitHub에 업로드

git push

이때부터 main에 새 개선판이 반영되고,
GitHub Pages가 main을 배포 중이라면 실제 사이트에도 새 버전이 배포됩니다.

==================================================
9. redesign이 마음에 들지 않을 때
==================================================

redesign을 main에 병합하지 않으면 됩니다.

기존 버전으로 돌아가기:

git switch main

main 브랜치는 그대로 유지되므로
redesign에서 큰 실수를 해도 기존 배포 버전에는 영향이 없습니다.

==================================================
10. 자주 쓰는 Git 명령어
==================================================

현재 상태 확인
git status

현재 브랜치 목록
git branch

현재 브랜치 이름만 확인
git branch --show-current

redesign으로 이동
git switch redesign

main으로 이동
git switch main

GitHub 최신 버전 가져오기
git pull

변경사항 스테이징
git add .

커밋
git commit -m "수정 내용"

GitHub에 업로드
git push

원격 변경사항을 내 커밋 앞에 반영
git pull --rebase

==================================================
11. 문제 발생 시 우선 확인 순서
==================================================

1. 현재 브랜치 확인

git branch

2. 현재 상태 확인

git status

3. GitHub 최신 상태 가져오기

git pull

4. 오류 메시지가 나오면 임의로 파일을 삭제하거나 덮어쓰지 말고
   오류 메시지를 그대로 복사해서 확인

특히 다음 명령은 의미를 모를 때 함부로 사용하지 않는 것을 권장합니다.

git reset --hard
git clean -fd
git push --force

이 명령들은 작업 내용을 삭제하거나 GitHub 이력을 강제로 바꿀 수 있습니다.

==================================================
12. 가장 간단한 일상 운영 요약
==================================================

작업 시작
→ 작업시작.bat
→ 현재 브랜치 확인
→ redesign이면 작업 시작

작업
→ VS Code / Codex
→ localhost에서 테스트

작업 종료
→ 작업종료.bat
→ 변경사항 확인
→ 커밋 메시지 입력
→ commit
→ pull --rebase
→ push

다음 PC에서
→ 작업시작.bat
→ git pull
→ 이어서 작업

==================================================
13. 권장 습관
==================================================

- 대규모 개선 작업은 redesign
- 실제 서비스 안정판은 main
- 브랜치 전환 전 git status
- 작업 시작 전 git pull
- 작업 종료 후 git push
- 오류가 나면 메시지를 지우지 말고 그대로 확인
- 커밋은 기능 단위로 자주 남기기
- main에 병합하기 전 localhost에서 충분히 테스트하기
